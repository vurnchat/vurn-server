# VurnChat v0.9 — Hybrid Ratchet Protocol (draft)

Status: accepted design, staged implementation.
Decisions locked with the project owner:

1. **Ratchet = hybrid, Signal-style**: an X25519 DH double ratchet provides
   forward secrecy (FS) and post-compromise security (PCS); a parallel
   ML-KEM-1024 ratchet (SPQR-style) is mixed into every message key so
   forward secrecy holds even against a quantum adversary that breaks the
   X25519 layer.
2. **Bootstrap = signed prekey in profile/invite** (PQXDH-lite): first
   messages of a session are protected by fresh KEM secrets, so FS covers
   the very first exchange, not just messages after a reply.

This is honest about what "post-quantum" means for the project from now on:
hybrid, like Signal — an adversary must break *both* the classical DH layer
and the ML-KEM layer.

---

## 1. Identity model (v0.9 profile bundle)

A user's profile/invite/contact payload carries, in one sealed blob:

| Key | Algorithm | Purpose |
|---|---|---|
| `ik_kem` | ML-KEM-1024 static pk | legacy compatibility; second KEM input to bootstrap |
| `ik_x`   | X25519 static pk | DH identity for X3DH-lite + ratchet root |
| `sig_pk` | ML-DSA-87 pk | sender authentication (already shipped in v0.7) |
| `spk_kem` | ML-KEM-1024 signed prekey pk | PQXDH-lite: fresh KEM input for session init |
| `spk_x`   | X25519 signed prekey pk | X3DH-lite: DH input for session init |
| `spk_sig` | ML-DSA-87 signature over `spk_kem ‖ spk_x` by the identity ML-DSA key | binds prekey to identity |

The client keeps the corresponding secret keys; the signed-prekey secret
pair is replaced on each re-registration and old prekey secrets are deleted
once all sessions that used them are closed or the prekey rotates.

Identity session id stays `SHA-256(ik_kem)` so relay routing / mailbox
grouping is unchanged.

## 2. Cryptographic primitives and KDFs

- DH: X25519 (RFC 7748). Shared secret 32 bytes.
- KEM: ML-KEM-1024 (as today). Shared secret 32 bytes.
- AEAD: AES-256-GCM. Key 32 bytes, nonce 12 bytes.
- KDF: HMAC-SHA256 (32-byte outputs). An HKDF-style expansion is built from
  two HMAC calls (labels below).

Chain step (per message within a chain). **Direction separation is
implicit**, not label-based: sending and receiving chains are distinct chain
keys seeded from different DH outputs, so the per-step KDF is identical for
both directions (sender and receiver must derive the same message key from
the same chain key):

    mk, ck' = HMAC(ck, 0x01), HMAC(ck, 0x02)

Message encryption material: `ek = HMAC(mk, 0x06)[0..32]`,
`nonce = HMAC(mk, 0x07)[0..12]`.

Root step (DH ratchet), Signal-style:

    rk' = HMAC(rk, 0x03 ‖ dh_out)
    ck_seed = HMAC(rk, 0x04 ‖ dh_out)

Hybrid mixing per message: the AEAD key is never the DH-chain key alone.
Each message carries a fresh KEM encapsulation to the peer's current
advertised ML-KEM ratchet key:

    final_mk = HMAC(dh_mk, 0x05 ‖ kem_ss)

The KEM secret `kem_ss` is generated by the sender per message (ML-KEM
encapsulation embeds fresh randomness) and never persists. The recipient
decapsulates with its advertised ML-KEM ratchet secret key; keep current +
previous to tolerate crossed messages (lag ≤ 1 chain).

## 3. Session state (per contact, persisted encrypted in IndexedDB)

    rk            32 B   root key
    dh_our        X25519 ratchet keypair currently advertised for inbound
    dh_peer       32 B   peer's latest advertised X25519 ratchet pk
    kem_our       ML-KEM ratchet keypair(s) advertised for inbound (≤2: current+prev)
    kem_peer      peer's latest advertised ML-KEM ratchet pk
    ck_send / ck_recv   sending and receiving chain keys
    n_send / n_recv / pn   message numbers (pn = length of *our previous
                           sending chain*, fixed when the chain closes)
    session_id    32 B, caller-supplied and identical on both sides
                           (bound into every AEAD header)

Send-chain opening is **deferred** (spec: deferring new ratchet key
generation): receiving a new peer chain sets up the receiving chain and
clears the sending chain; the fresh X25519 ratchet keypair + KEM keypair for
the reply are generated when the next message is actually sent, so the DH
secret that seeds the next sending chain is exactly the one the peer used to
derive its receiving chain.

The responder derives its initial receiving chain lazily on its very first
decrypt (the initiator's ephemeral key only appears in that first inbound
header) and pre-generates a KEM ratchet key at session start, because the
initiator encapsulates to it from her very first message.

Skipped-message-key store: none initially. We rely on the relay's ordered,
exactly-once delivery (v0.6.6 watermark + Sled drain). A gap or out-of-order
message is a hard protocol error that surfaces as a "session out of sync"
notice; recovery = the peer starts a new session (fresh init). Documented
limitation, revisit if multi-node DHT replication makes reordering plausible.

## 4. Message flow (double ratchet, DH + KEM mixing)

Send (we→peer), Signal RatchetEncrypt extended:

1. If no sending chain is open: open one. Generate a fresh `dh_our` keypair
   (and set the advertise flag so a fresh `kem_our` is advertised); compute
   `dh = X25519(dh_our.sk, dh_peer)`; `rk, ck = root_step(rk, dh)` → new
   sending chain; `n_send = 0`. `pn` was already fixed when the previous
   chain closed. The first message of the new chain advertises the fresh
   `kem_our` public key (0x02 flag).
2. For the actual message: advance `ck_send`, derive `mk`, encapsulate a
   fresh ML-KEM secret to the peer's latest advertised `kem_peer` and compute
   `final_mk = mix_kem(mk, kem_ss)`; AEAD-encrypt with AAD =
   `session_id ‖ header`.
3. Header carries `dh_pub`, `pn`, `n`, optional 0x02 (kem_pk advertisement)
   and 0x04 (kem ciphertext) fields.

Receive (peer→we), Signal RatchetDecrypt extended:

1. First message ever (responder): derive the initial root + receiving chain
   from `dh = X25519(session-start sk, header.dh)` — the initiator derived
   the same value for her first sending chain.
2. If `header.dh != dh_peer`: peer opened a new chain. Validate `header.pn ==
   n_recv` (their previous chain fully consumed); `dh = X25519(dh_our.sk,
   header.dh)`; root_step → new receiving chain; `n_recv = 0`; adopt
   `dh_peer = header.dh`; clear the sending chain (reopened on next send).
   If `header.dh == dh_peer`: require `header.n == n_recv` (ordered,
   exactly-once), else `OutOfOrder`.
3. Advance `ck_recv`, derive `mk`; decapsulate the header KEM ciphertext
   with the advertised KEM secret keys (newest first); `final_mk`;
   AEAD-decrypt. On success record the peer's freshly advertised `kem_pk`.

Note (SPQR layering): we implement per-message KEM mixing (formulation (b));
it costs one 1568-byte KEM ciphertext per message on the wire. If message
size matters later, switch to (a) per-turn encaps (SPQR chunking is an
optional optimization, not a security requirement).

## 5. Bootstrap — PQXDH-lite session init (Alice → Bob first message)

Alice fetches Bob's profile bundle (username search or invite). Alice:

1. Generates ephemeral X25519 keypair `ek_x` and ephemeral ML-KEM pair
   `ek_kem` (advertised in init message).
2. Computes:
   - `dh1 = X25519(ik_x_A, spk_x_B)` (static → signed prekey)
   - `dh2 = X25519(ek_x_A, ik_x_B)`  (ephemeral → static)
   - `dh3 = X25519(ek_x_A, spk_x_B)` (ephemeral → signed prekey)
   - `kem1 = KEM.Encaps(spk_kem_B)`  (ephemeral → PQ signed prekey)
   - `kem2 = KEM.Encaps(ik_kem_B)`   (ephemeral → PQ static; optional)
3. `seed = HKDF(dh1‖dh2‖dh3‖kem1‖kem2, info="vurn-init")` → root `rk`.
   Alice can now open the first sending chain (her `dh_our`/`kem_our` were
   generated above and advertised in the init message).
4. Sends init message: her identity keys already known to Bob; header adds
   `ek_x.pub`, `ek_kem.pub`, the two KEM ciphertexts, and the first DH chain
   message encrypted as in §4.

Bob receives the init while offline (mailbox), and:

1. Computes the same DH values with his secret keys and decapsulates both KEM
   ciphertexts (he deletes the signed-prekey secret only after prekey
   rotation, not per session — a signed prekey is multi-session by design).
2. Derives the same root, records Alice's advertised `ek_x`/`ek_kem` as
   `dh_peer`/`kem_peer`, opens the receiving chain, decrypts message 1.
3. On his first reply he runs the §4 send path with fresh ratchet keys.

Concurrent inits (both send first) are handled like concurrent sessions in
Signal: both init messages decrypt independently; each side adopts the
session whose first *continuation* it processes; stale half-sessions expire.
Single-device profile keeps this manageable.

## 6. Security analysis (claims)

- FS (classical): chain keys and root keys are HMAC-forward-only. The DH
  ratchet secret that seeds a receiving chain is deleted as soon as the
  owner sends its next message (fresh ratchet keypair): a state stolen
  before that send cannot derive any chain seeded afterwards. Concretely, a
  compromise is sealed at the next ratchet advance (one reply) on the
  compromised side; the owner's own messages already sent are likewise
  past. Within a single un-replied turn, messages are encrypted under keys
  derived from the same DH secret — inherent to the double ratchet, same as
  Signal. Verified by the `test_forward_secrecy_old_state_cannot_read_new`
  property test (thief reads the pre-advance message, is locked out of
  everything after the owner's next reply).
- FS (quantum): the per-message ML-KEM secret mixed into `final_mk` is
  deleted/never stored; a quantum adversary breaking X25519 learns only the
  DH half of each message key.
- PCS: a fresh DH ratchet + fresh ML-KEM ratchet keys are introduced on
  every peer chain open; after one honest round-trip a compromise is
  sealed.
- What this does NOT provide (unchanged): metadata privacy (relay sees the
  social graph, sizes, timing); server-side usernames are dictionary-
  attackable; no deniability layer; compromise of the local encrypted vault
  exposes everything in it at that moment (standard for single-device).

## 7. Staged implementation plan

Stage A: **DONE.** `vurn-core/src/ratchet.rs`: KDFs, X25519 double ratchet
with per-message ML-KEM-1024 mixing, deferred send-chain opening, responder
lazy init + pre-generated KEM key, session serialize/deserialize, and 7
property tests (ping-pong, burst turns, distinct ciphertexts, replay
rejection, tamper, persistence mid-conversation, forward secrecy,
reordering, sustained pseudo-random traffic). All 41 `vurn-core` tests
green. New deps in core: `x25519-dalek`.
Stage B: **DONE.** `vurn-core/src/identity.rs` — `IdentityBundle`
(ik_kem, ik_x, sig_pk, spk_kem, spk_x, spk_sig) with versioned
encode/decode (0x09 magic, legacy-tolerant: v0.7 payloads decode with
empty prekey fields), `build_identity_bundle` (fresh signed prekey,
ML-DSA-bound via raw signature over `spk_kem ‖ spk_x`),
`verify_prekey`, plus v9 variants of profile registration/resolution
and invite generate/parse. Core version bumped to 0.8.0. 51 tests
green. Stage C (client wiring) still requires re-registration of test
usernames.
Stage C: client wiring — per-contact session store in IndexedDB (encrypted),
send/receive paths use sessions, init on first message to a new contact,
session persistence across reloads, legacy (v0.7) ciphertext fallback,
out-of-sync UX.
Stage D: release, build, deploy web + verify two-account E2E.

## 8. Wire/API surface changes (for Stage C)

- Core exposes: `Session` (start_alice/start_bob/encrypt/decrypt/
  to_bytes/from_bytes), `SessionStart` (bootstrap root, shared session_id,
  initial DH keypairs, initiator KEM keypair), `identity.rs` v0.9
  encode/decode, new constants.
- `SessionStart.session_id` must be identical on both sides (it is bound
  into every AEAD header); derive it deterministically from the two identity
  keys at bootstrap, e.g. `SHA-256(ik_x_A ‖ ik_x_B)`.
- Frame payload per message becomes one ratchet package (header + AEAD);
  existing relay framing `[2B id_len][id][package]` and mailbox framing
  unchanged (opaque bytes).
- Server: no changes required.
